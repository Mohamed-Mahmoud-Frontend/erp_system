# مميز — دليل النشر والتحديث

النظام يتكون من واجهة Next.js وخدمات Supabase للبيانات والدخول. مجلد `.deploy` يحتوي سياسة ترحيلات قاعدة البيانات، ولا تُشغّل الترحيلات عند فتح الموقع أو داخل `next build`.

## الحالة الحالية

- تم التحقق حيًا من تطابق سجل الترحيلات `0001` إلى `0024` بين المحلي وSupabase يوم 9 سبتمبر 2026.
- المسار الجاهز هنا هو Vercel للواجهة + Supabase للبيانات. تشغيله الفعلي يحتاج ربط حساب الاستضافة وإضافة الأسرار التالية.
- النشر التلقائي لا يعمل قبل ضبط متغير GitHub `DEPLOY_ENABLED=true` ودمج العمل في `main`.
- `vercel.json` يعطل النشر المباشر عبر تكامل Git حتى لا يسابق نشر الواجهة ترحيل قاعدة البيانات. GitHub Actions هو مسار النشر الوحيد بعد الإعداد.

## إعداد مرة واحدة

1. أنشئ/اربط مشروع Vercel بالمستودع واضبط Node.js 22.
2. ضع متغيرات `.env.example` في إعدادات Vercel للإنتاج. `NEXT_PUBLIC_SITE_URL` هو رابط الموقع الفعلي، ومفتاح `SUPABASE_SERVICE_ROLE_KEY` سري للخادم فقط.
3. في GitHub أنشئ Environment باسم `production`، وأضف: `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`, `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `SUPABASE_PROJECT_ID`.
4. راجع روابط الدخول المسموح بها وSite URL في Supabase Auth لتطابق الدومين الجديد.
5. فعّل حماية `main` واطلب نجاح Quality checks قبل الدمج. اضبط `DEPLOY_ENABLED=true` بعد اكتمال الإعداد.
6. تأكد من نسخة احتياطية حديثة قابلة للاسترجاع قبل أول إصدار يغيّر البيانات.

لا توضع الأسرار في Git أو في وصف PR أو في ملف PDF. لا تنسخ `.private` أو `.backups` إلى الاستضافة العامة.

## دورة كل ميزة

```bash
git switch -c feat/feature-name
# implement one feature
npm run db:check
npm run verify:business
npm run verify:permissions
npm run build
npm run typecheck
npx eslint . --max-warnings=0
git add <explicit-feature-files>
git commit -m "feat(scope): describe the user-visible behavior"
git push -u origin feat/feature-name
```

أنشئ PR إلى `main`. النشر يبدأ بعد الدمج: فحوصات → بناء Vercel بالإعدادات الحقيقية → معاينة ترحيلات Supabase → تطبيق الجديد فقط → نشر الواجهة المبنية. يوجد قفل يمنع عمليتي نشر إنتاج متزامنتين، ولا يلغي ترحيلًا جاريًا بسبب commit أحدث.

## قواعد قاعدة البيانات

- لا تستخدم `db reset` أو `--include-seed` أو `migration repair` في الإنتاج كجزء من تحديث يومي.
- لا تعدّل ملفات ترحيلات سبق تطبيقها. استخدم `npx supabase migration new descriptive_name` ثم `npm run db:manifest` لتسجيل الملف الجديد.
- `migrations.json` يحفظ بصمات الملفات الحالية مع تطبيع نهايات الأسطر، لمنع تغير البصمة بين Windows وLinux.
- CI يقارن البصمات أيضًا بالنسخة السابقة حتى لا يمكن تجاوز الفحص بتغيير الملف وبصمته معًا.
- تحديث واجهة فقط: `db push` لا يعيد تشغيل الملفات المسجلة. فشل اختلاف السجل يوقف الإصدار ويحتاج مراجعة؛ لا يتم إصلاحه تلقائيًا.
- استخدم تغييرات متوافقة مع النسخة السابقة: أضف الحقل أولًا، انشر الكود، انقل البيانات، ثم احذف القديم في إصدار لاحق بعد انتهاء استخدامه. لا يمكن ضمان عدم التعطل عند حذف عمود يعتمد عليه الإصدار الجاري.

## التحقق والرجوع

بعد النشر تحقق من `/api/health` ثم تسجيل الدخول وفتح العملاء وإجراء قراءة من حساب محدود الصلاحيات. `/api/health` يثبت عمل خادم التطبيق فقط، وليس سلامة Supabase أو Google.

عند فشل البناء أو الترحيل لا يبدأ نشر الواجهة. لو طبقت ترحيلات ثم فشل رفع الواجهة، تبقى تغييرات القاعدة؛ التوافق مع النسخة السابقة مطلوب. عند مشكلة في الواجهة ارجع لإصدار Vercel السابق بعد التأكد من توافقه مع المخطط الحالي. لا تشغّل عكسًا تلقائيًا لترحيلات البيانات ولا تسترجع نسخة فوق الإنتاج دون إجراء استعادة مستقل.

لكل إصدار `NEXT_DEPLOYMENT_ID` مختلف مأخوذ من commit SHA، لمساعدة Next.js على اكتشاف اختلاف نسخة المتصفح والخادم. هذا لا يحفظ نموذجًا غير مرسل ولا يغني عن توجيه الطلبات الصحيح أثناء تحديث سيرفرات متعددة.

## لو التشغيل على VPS

لا تعمل `git pull && next build` داخل مجلد الإصدار الذي يخدم المستخدمين. ابنِ إصدارًا جديدًا في مجلد/حاوية منفصلة، افحصه على منفذ داخلي، طبّق الترحيلات المتوافقة، ثم حوّل reverse proxy إليه مع إبقاء السابق للرجوع. اضبط مفتاح `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` ثابتًا وسريًا عند البناء بين النسخ، ومعرّف إصدار جديدًا لكل بناء. سكربت نقل المرور يحتاج عنوان السيرفر وطريقة التشغيل؛ لم يُفترض وجودهما هنا.

## النسخ والمزامنة

مهام Google Drive والنسخ الحالية تعمل على جهاز Windows المستقل. نشر Next.js على Vercel لا ينقل هذه المهام تلقائيًا. أبقِ جهازها يعمل أو خطط لنقلها إلى عامل تشغيل دائم مع المفاتيح المخزنة بأمان؛ لا تشغّل نسختين من المجدول معًا. لا تشغّل نسخ pg_dump طويلة داخل طلب صفحة أو Server Action.
